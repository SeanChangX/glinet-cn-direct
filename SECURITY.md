# Security policy

This project generates rules that decide which traffic bypasses a VPN tunnel. A
bad rule does not crash anything — it silently sends traffic you believed was
protected out over the open network. The whole design follows from that.

No security guarantees are made. What follows is what the system actually does,
so you can judge it for yourself.

## Reporting a vulnerability

Report suspected security problems privately through GitHub's
[private vulnerability reporting](../../security/advisories/new) rather than in
a public issue.

Useful things to include: what you observed, which artifact and release, and —
if it is a routing problem — the specific rule and the destination it wrongly
matches.

If you believe a **currently published list is unsafe**, say so in the first
line. Meanwhile, protect yourself immediately by pointing your router at a
previous release tag instead of the `release` branch, or by removing the
subscription URL.

Please do not report incorrect geolocation for a single address as a
vulnerability — no GeoIP database is perfect. Open an issue instead, ideally
upstream.

## Threat model

### Assets

- the integrity of the published routing policy;
- users' expectation that non-Chinese traffic stays inside the VPN tunnel;
- the integrity of generated artifacts in transit and at rest;
- CI publishing credentials.

### Threats and mitigations

| Threat | Mitigation |
| --- | --- |
| Upstream account compromise injects malicious rules | Reserved-range checks, broad-prefix limits, never-direct domain tripwires, IP canaries, coverage ceiling, diff thresholds against the last release, and an independent second upstream that must agree |
| Upstream accidentally publishes bad data | Same gates. A build that trips any of them publishes nothing |
| Upstream build script is malicious | No upstream code is ever executed. Data files are downloaded and parsed; no clone, no `build.sh`, no upstream workflow |
| A source URL is silently redirected | Only HTTPS, only allowlisted hosts, and only sources described in `config/expected-sources.json`. Every redirect hop is re-validated |
| Upstream serves an HTML error page | Responses starting with HTML/XML markers are rejected outright rather than parsed into zero rules |
| A moving branch changes under us | Branches are resolved to a commit SHA first; content is downloaded from a SHA-pinned URL and that SHA is recorded in `metadata.json` |
| Dependency compromise | The generator has **zero** runtime dependencies — Python standard library only. `pytest` is installed in the test job alone |
| GitHub Action compromise | All Actions are pinned to full 40-character commit SHAs, and only GitHub-maintained Actions are used |
| Compromised CI token | Default `permissions: contents: read`. Only the publish job gets `contents: write`, and only after every gate passed. No `pull_request_target`. No PAT — `GITHUB_TOKEN` only |
| Malicious pull request | PR builds are read-only and never receive publishing credentials |
| Parser bug produces valid-looking garbage | Generated bytes are re-validated against the GL.iNet grammar, then re-checked by an independent shell script (`scripts/acceptance-checks.sh`) that re-runs after the artifact crosses a job boundary |
| Unexpected rule expansion | Coverage ceiling, per-set size envelope, rule-count and address-coverage change limits |
| Maintainer mistake | Branch protection on `main`, required CI, deterministic output, published checksums, and immutable release history for comparison |
| Compromised maintainer account | Not mitigated. Immutable tagged releases and recorded upstream SHAs make tampering detectable after the fact, not preventable |

### Explicitly out of scope

- Correctness of upstream geolocation data. This project validates *shape and
  safety*, not whether a given prefix is genuinely in China.
- GL.iNet firmware behavior. How the router parses and applies a syntactically
  valid list is outside this project's control.
- Your VPN provider, your DNS, and everything else on your network.

## The fail-closed rule

Every gate can only *reject*. There is no path in the code that repairs
suspicious data and continues.

On failure the workflow:

```text
DOES NOT modify the release branch
DOES NOT create a GitHub Release
DOES NOT overwrite known-good artifacts
```

and reports why, in this shape:

```text
SECURITY GATE FAILED

  gate  : ipv4:hard-prefix-limit
  reason: network(s) at or broader than /4 are never acceptable: 0.0.0.0/0

Publication blocked. The previous release remains active.
```

The previous list keeps serving until a human looks at it. A stale correct list
is safer than a fresh suspicious one.

## Verifying what you received

Every release publishes `checksums.txt` and `metadata.json`:

```bash
sha256sum -c checksums.txt
```

`metadata.json` records, for each upstream file: the exact URL, the resolved
commit SHA, the SHA-256 of the downloaded bytes, the download timestamp, and how
many entries were read, accepted and rejected. Builds are deterministic, so you
can re-fetch those pinned inputs and confirm the output byte-for-byte.

Releases also carry GitHub build provenance attestation where available:

```bash
gh attestation verify cn-ipv4.txt --repo SeanChangX/glinet-cn-direct
```

Attestation is optional hardening. The basic subscription flow does not depend
on it.

## Changing a safety threshold

Thresholds live in `config/policy.toml`. Loosening one is a security change, so
treat it as such: say in the pull request which build tripped the gate, what the
audit report showed, and why the movement was legitimate rather than an attack.

Raising a threshold to make a red build go green, without understanding why it
went red, defeats the entire point of this repository.
